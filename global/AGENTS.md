# 工程风格：写给人维护的代码

## 规模
- 先做最小可用实现；不为假想需求加抽象、加层、加配置。
- 一次改动只解决一件事；不顺手新增包、文档、脚本、计划文件。
- 一个提交只做一件可描述的事；不做"checkpoint"式的大提交。
- 优先使用现成工具和原生配置（格式化器、lint 规则、框架自带机制）；不为一次性需求自建脚本、框架或基线文件。
- 只在系统边界（用户输入、外部服务、文件、网络）校验和处理错误；内部调用信任类型和调用方约定，不为不可能出现的状态加判空、兜底、重试。
- 依赖只有一种实现时，不写接口断言链、兼容分支或降级路径；出错就返回错误，不静默吞掉。
- 需要跨进程一致性时，先用数据库事务、行锁和唯一约束；不自建 epoch、fence、lease 这类协议，确有必要时在设计里说明数据库机制为什么不够。
- 未上线的数据库迁移可以合并；已经应用到任何环境的迁移不再修改。

## 命名与概念
- 只用领域里已有的词或项目术语表里的词。新概念先写进术语表再使用。
- 同一概念只有一个名字；不让 grant / authority / permit / lease / fence 这类近义词并存。
- 名字里不留历史痕迹：native、legacy、retired、original、new、v2、final。
- 标识符一般不超过 4 个词；测试名描述行为，不写成一整句话。

## 结构
- 新建包/模块前先确认现有包放不下；不到 150 行、只有一个文件的包通常应并入别处。
- 每个包/模块开头用一句话说明职责。
- 新写的函数不超过 80 行，文件不超过 600 行；计费、转发、鉴权等核心路径优先保持可读。
- 一行只写一条语句；代码行不超过 120 字符；交给格式化工具，不手工挤压。

## 修改已有代码
- 长度和行宽规则只约束本次新写或修改的代码；不要为满足规则重排、折行或拆分未触及的旧代码。整理旧代码另开任务。
- 热修复保持最小 diff：只改与问题相关的代码，让审阅者一眼看出改了什么。

## 测试
- 按被测行为组织测试文件；不按 review / audit / regression / 第几轮命名。
- 修 bug 时把回归用例加进对应行为的测试文件。
- 测试覆盖需求里的行为和真实出现过的 bug；不为每个分支、每种非法输入、每种内部状态组合各写一个用例。
- 测试量与改动相当：小修复配一两个测试；新增测试明显多于生产代码时，先合并重复用例，删掉只验证防御分支的用例。
- 不写断言源码文本的测试。

## 文字（注释、文档、spec、界面文案）
- 写完整、自然的句子；不用压缩电报体，不把数字和单词粘在一起（写 "2026-10-28 起"，不写 "The2026-10-28"）。
- 注释解释"为什么"，不复述代码，不写过程自述；不罗列代码不做什么（"not X""never Y"），除非那正是读者最容易误解的地方。
- spec/设计文档只描述当前状态；改变规则时直接改写原文，不写 "supersedes"、不留历史层。优先合并进已有文档，不为每个功能新建一份。
- 规划文档只写决策和步骤，不堆免责声明（"does not authorize""is not proof of"）。
- 界面文案面向用户：说用户能做什么、会发生什么；不暴露内部不变量和工程术语。
- 不提交工作计划、发布流水账、验证日志、截图、二进制。发布记录写进 CHANGELOG 几行。

## 排查问题
- 先拿证据再下结论：复现问题，每次只改一个变量做对照，记录每次实验的输入和结果。
- 材料不完整（截断、抽样、只读了部分代码）时只能提出假设，不能写成确定结论。
- 判断"复现""通过"是否成立时，看与问题相关的条件（错误码、关键字段、行为），不要求无关细节逐字节一致。
- 不通过规避外部服务的明确限制让功能可用；遇到限制时说明限制，并给出服务方支持的做法。

## 副作用与汇报
- 安装依赖用不改写锁文件的方式（pnpm install --frozen-lockfile、npm ci 等）。
- 提交前检查 git status 和 git diff --stat；每个不在计划内的变更都要查清来源。
- 只在需要用户决定时停下（需求取舍、改变行为、越权或涉及线上）；其余情况自行推进，最后统一汇报。项目或任务另有要求时以其为准。
- 如实汇报：未做的、失败的、跳过的单独列出，计划中的检查不写成已完成。

## 结束前自检
- 这次新增了哪些包、文件、概念词？每一个是否必要？
- 新增的每个校验、兜底和测试，防的是哪个真实会发生的情况？
- 一个新加入的人只看名字和注释，能否理解它是做什么的？
