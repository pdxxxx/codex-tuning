# 发布

适用：代码已经验收，授权 Codex 发布到生产。下面是不做备份和演练的简单发布；需要备份或灰度时，在第 3 步前后加上对应要求。

```
我授权把当前 HEAD 发布到 <环境>。

1. 发布前：在当前 HEAD 上跑完整门禁（<门禁命令>），全部通过才继续。
2. 按 <发布文档> 从 git 构建镜像，打包时用 git archive，不要直接用工作区的文件（Windows 下的工作区可能带 CRLF）。
3. 把每个数据库迁移的哈希与生产数据库的记录逐一对照，全部一致才能继续。有不一致的就停下报告，不要修改数据库里的校验值，也不要放宽校验。
4. 替换应用容器。数据库、缓存、secrets 和运行配置都不动。
5. 发布后检查：
   - 健康检查接口返回 200，容器没有重启循环；
   - 真实登录一次，主要页面各打开一次，页面上没有错误提示；
   - 控制台和网络面板中，除了 <已知的正常现象，例如登录前 /api/auth/me 返回 401> 以外，没有 4xx/5xx 请求，也没有 JS 异常。出现错误时记下具体的请求 URL。
   - 不修改业务数据，不发起会消耗外部额度的请求。
6. 第 5 步失败时，切回旧镜像并停下，不要自行排查或修改代码。
7. 成功后在 CHANGELOG.md 中用几行记录本次发布的内容，然后做一次本地提交。不要新建发布记录文件。

完成后告诉我：新旧镜像摘要、迁移对照结果、各项检查结果、CHANGELOG 的提交号。
```

发布失败、需要排查时，先让它只做诊断，不要同时修复和重发。拿到根因后，判断修法应该是一次性的，还是应该永久固定到仓库里，再决定下一步。
