# /goal 模板

goal 模式会连续推进，中途不会停下等你。所以所有需要你决定的事，都要在开始前写进任务文件或这段文本里。

## 开始前确认

- [ ] 需求和取舍已经写进任务文件（prd、design、implement），`implement.md` 末尾写明规划已批准。
- [ ] 每条完成标准都能用命令判断。
- [ ] 不涉及发布、线上服务或真实凭据。
- [ ] 这个工作区没有其他会话在改文件。
- [ ] `~/.codex/config.toml` 的 `[goals]` 中设置了 `max_goal_token_budget`。

## 模板

```
/goal 完成 <任务或一组任务>。我已授权你自行规划和实施，中途不需要等我确认；全部完成后我统一审阅。

## 任务
<任务路径；或者按执行顺序列出子任务，每项写清目标和可度量的终点，例如"超过 80 行的函数全部拆分，并删除对应的豁免规则">

## 全局约束
- 不改变运行时行为。不改：<数据库结构、迁移、API 路径和字段、序列化存储值、环境变量、日志和事件名……>。
- 不修改：<排除的目录>。
- 每个子任务至少一个本地提交，一个提交只做一件事；纯移动、纯重命名和结构改动分开提交。不 push，不部署，不访问线上服务，不使用真实凭据。
- 每次提交前通过：<门禁命令>。

## 必须停下来问我的情况
- 只有改变行为才能让测试通过；
- 需要改动"不改"清单中的任何一项；
- 改动量明显超出预期（例如单个子任务的 diff 超过 <N> 行），需要拆分或缩小范围；
- 出现与任务无关的门禁失败，而且无法确认是原本就存在的问题。

## 完成时交付
写 <路径>/final-report.md，包括：每个子任务的提交（hash 和说明）；关键指标的前后对比；保留的例外及原因；所有门禁的最终输出摘要；建议我重点审阅的提交。
```

## 完成后

按 `playbook/review-checklist.md` 的"审交付"部分逐项核对。重点看逻辑结构变化最大的几个提交，确认它们真的没有改变行为。
