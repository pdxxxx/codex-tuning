# 审阅清单

## 审规划（design、implement）

- **范围**：写入的路径是否只包含任务需要的部分？有没有"顺手"的改动？
- **新增物**：新增了哪些包、脚本、配置、基线文件？能不能用现有工具的原生机制代替？
- **命名**：新文件名、新标识符是否沿用了正要清理的旧术语？
- **篇幅和文风**：规划是否超过 150 行？是否堆满免责句？写进 spec 的内容是否是人能读的句子？
- **一致性**：同一个参数在不同地方的取值是否一致（例如行宽的 tab 宽度）？
- **证据**：基线数字能否用给出的命令复现？
- **风险**：是否在绕过外部服务的明确限制？是否会改变线上行为，例如让一段从未生效的代码开始生效？
- **停止条件**：什么情况下停下？范围太宽会频繁停，太窄会越权。
- **验收**：每条验收标准是否有能运行的命令？

## 审交付

- 用 `git log --stat` 和 `git show --stat <hash>` 看每个提交的范围，和报告是否一致。
- 自己跑一遍关键数字：度量脚本、验收用的 grep、测试数量。
- 看 `git status`：有没有意外变更，例如锁文件、生成文件、日志？来源是什么？可以对比文件修改时间追查。
- 大 diff 先看 `git diff -w --stat`，把格式变化和逻辑变化分开。
- 抽读一两个文件：文风是否真的改善，是否丢了规范要求。
- 没通过的门禁：是否证明了是原本就存在的问题（在修复前的代码上复现同样的失败）？
- 涉及线上时：发布前核对配置（尤其是第一次生效的配置），在与生产相同的系统上跑测试，发布后做一次线上验证。

## 回复 Codex 时

- 一条回复只给一个动作指令。"改完停下"和"改完继续"不要写在同一句里。
- 否决一个方案时，用一句话说明原因，并给出替代方案。
- 先肯定做对的部分。下一轮它会保留这些做法。
