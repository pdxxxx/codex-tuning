# 工作流

## 规则放在哪

| 位置 | 什么时候生效 | 适合放什么 |
| --- | --- | --- |
| `~/.codex/AGENTS.md`（来自 `global/AGENTS.md`） | 每次会话开始 | 跨项目通用的工程风格，控制在 60 行左右 |
| 项目根目录 `AGENTS.md` | 进入项目时 | 项目边界、门禁命令、spec 和术语表的入口 |
| 项目 spec | 按任务加载 | 目录结构、质量上限、术语表、各模块的当前规则 |
| `UserPromptSubmit` hook | 每一轮 | 3 行以内的摘要；上下文压缩后仍然在 |
| `Stop` hook | 每轮结束 | 能用程序判断的规则：命名、函数长度、行宽、锁文件、文档文风 |
| lint 和 CI | 提交、合并时 | 最终兜底，不依赖是哪个 agent、有没有开 hook |
| skill | Codex 觉得相关时才读 | 较长的按需流程；不保证加载，不要放必须遵守的规则 |

两条经验：

- 规则写在文档里，agent 依然会违反。能量化的规则一定要落到 hook 或 lint。
- agent 照抄它读到的文本。spec 写成什么文风、用什么术语，代码就是什么样子。先修 spec，比加规则有效。

## 一个任务的节奏

1. **定需求**：写 `prd.md`。验收标准尽量写成能直接运行的命令。
2. **Codex 规划**：用 `prompts/plan-task.md`。让它写完规划就停下。
3. **审规划**：对照 `review-checklist.md`。回复用 `prompts/review-feedback.md`，明确写"改完停下"或"改完继续"。
4. **执行**：普通模式；或者在所有决定都已写进任务文件后，用 `/goal`（`prompts/goal.md`）。
5. **验收**：自己复现关键数字，对照 `review-checklist.md` 审交付，不只看 Codex 的报告。规范较长时，要求它提交逐条的规格对照表（`prompts/spec-check.md`）。
6. **沉淀**：新发现的行为写进 `lessons.md`；能自动检查的，补进 hook 或 lint。

## 什么时候用 /goal

适合：需求和取舍已经写进任务文件，完成标准能用命令判断，不涉及线上。

不适合：需求还在讨论、要在几个方案间取舍、要发布或访问线上服务。

审规划是人介入最有价值的时刻。goal 模式会跳过所有停顿点，所以必须先把决定写进文件。开始前：

- 在 `implement.md` 末尾写明规划已批准；
- 同一个工作区同时只跑一个 goal，否则 Stop hook 和提交会互相串台；
- 在 `~/.codex/config.toml` 的 `[goals]` 中设置 `max_goal_token_budget`，防止它卡住时无限消耗；
- 把"必须停下问我"的情况写清楚，范围要窄。

## 排查线上问题

不要靠读代码推断根因。用 `prompts/real-debug.md`：本地复现，每次只改一个变量，设定请求预算，记录每次实验，再用同一个请求验证修复。

## 发布

用 `prompts/release.md`。发布前必须把迁移哈希与生产数据库逐一对照；检查条件要排除已知的正常现象，例如登录前的 401。

## 界面改造

Codex 能把界面实现准确，但做不出好看的设计。先写可以在浏览器里打开的参考稿和精确到数值的设计规范，再分阶段实施，每个阶段截图审阅。完整做法见 `ui-redesign.md`。

## 新接手一个仓库

先运行 `python tools/audit_repo.py <repo>`，再用 `prompts/audit-codebase.md` 做审查。根据结果决定先做哪件事：修 spec、加门禁，还是重构。顺序通常是：

1. 修正 agent 读到的指导文本（spec、术语表、项目 AGENTS.md）；
2. 加门禁，用基线豁免旧问题，只拦新问题；
3. 最后才是重构旧代码，每修好一处就删掉一条豁免。
