# Codex 行为观察与对策

来源：一个由 Codex 在一周内写成的 Go/React 项目（约 6.6 万行生产代码、6.4 万行测试、5 万多词的文档和 spec），以及随后的审查、规范整理、门禁建设和一次线上问题排查。每一条按现象、原因、对策记录。

## 1. 照抄输入文本的文风和术语

- **现象**：代码注释里 exact、proof、fence、lineage 反复出现；界面文案里出现 "checked stop""fence new work" 这类工程术语。
- **原因**：spec 用压缩的法律条文体写成，数字和单词粘连，自造术语密集。agent 照着写。
- **对策**：先修 spec：制定写作规则，建立术语表，把文档改写为只描述当前状态。只加规则、不修输入，效果有限。

## 2. 空模板 spec 等于没有约束

- **现象**：目录结构和质量规范的 spec 还是 "(To be filled by the team)"。结果是 31 个后端包，最长的函数 437 行。
- **对策**：项目初期就从真实代码中归纳结构和质量规范，写明量化上限，并附上真实文件作为示例。

## 3. spec 被当成变更日志

- **现象**：每做一个功能就新增一份 spec，新规则用 "supersedes" 叠在旧规则上，阅读顺序要层层跳转。
- **原因**：spec 更新类技能要求"每次都沉淀契约"，但没有要求合并和改写。
- **对策**：写作规则要求只写当前状态、直接改写原文、优先合并进已有文档。

## 4. 材料不完整时下确定结论

- **现象**：根据一份被截断的 256 KiB 请求体，断言某类条目是"确定的不兼容项"。拿到完整采集后，发现真正的原因是另一类条目。
- **对策**：要求区分"假设"和"结论"。条件允许时，用真实复现和单变量对照来取证。

## 5. 字面执行停止条件，变得过度谨慎

- **现象**：提示词里写了"逐字节一致"和"复现不了就停下"。结果它因为 8 字节的时区差异，判定"未复现"并停下。
- **对策**：写清判定标准的本意，例如"错误码和参数一致即为复现"。把停止条件收窄到真正需要人决定的情况，见 `prompts/unblock.md`。

## 6. 倾向自建框架

- **现象**：为了豁免历史 lint 违规，计划新写两套脚本、JSON 基线和对应的测试，而 golangci-lint 和 ESLint 的原生机制就能做到。
- **对策**：要求优先使用工具的原生机制。审规划时专门看"新增了哪些脚本和框架"。

## 7. 规划冗长，免责句堆叠

- **现象**：300 多行的 design，反复出现 "does not authorize""is not proof of"。
- **对策**：提示词里给出篇幅上限，并明确"只写决策和步骤，不写免责声明"。下一次规划就降到了 115 行。

## 8. 意外的副作用

- **现象**：一次隐式的 `pnpm install` 用新版 pnpm 重写了锁文件，丢掉了安全版本覆盖。agent 发现了变更，却不知道来源。
- **对策**：要求安装依赖时冻结锁文件。提交前看 `git status`，用文件修改时间追查来源。Stop hook 会检查"锁文件变了，清单却没变"的情况。

## 9. 全局规则放大了热修复的 diff

- **现象**：在一个旧仓库做热修复时，为了满足"函数不超过 80 行、行不超过 120 字符"，顺手重排和拆分了周围的旧代码。一个小修复变成了 224 行的 diff。
- **对策**：长度规则只约束新写和修改的代码。Stop hook 对已经超长的旧函数，只在明显增长时提醒。不打算整改的旧仓库，可以用 `.codex-style.json` 关闭检查。

## 10. 停顿点是人介入最有价值的时刻

- **现象**：几次关键纠偏都发生在审规划时：度量脚本不该嵌进 spec、合并后的文件名沿用了旧术语、不该自建 lint 框架、不该绕过上游限制。
- **对策**：goal 模式只用于"决定已经写进任务文件"之后的执行阶段。

## 11. 会执行顺带写的授权

- **现象**：审阅回复末尾写了一句"改完直接 start 并实施"，它立即执行完了。而人还以为它在等审阅。
- **对策**：每条回复只给一个明确的动作指令，见 `review-checklist.md`。

## 12. 为了让功能可用，会提出绕过外部限制的方案

- **现象**：上游明确把某些工具保留给自己使用，并强制校验其 schema。为了绕过校验，它提出给这些工具改名伪装。
- **对策**：审规划时专门检查是否在规避服务方的明确限制。这类方案直接否决，改走服务方支持的路径，例如路由到合适的账户类型，或者返回可操作的错误。

## 13. 过时的指引会把 agent 引到错误的位置

- **现象**：项目 AGENTS.md 仍然指向另一个仓库的任务目录。
- **对策**：AGENTS.md 只写稳定的边界和门禁；任务的位置变化时，同步修改它。

## 14. 防御性代码和测试过量，简单任务耗时成倍增长

- **现象**：另一个 Codex 写成的 Go 网关项目里，修 bug 的提交测试代码普遍多于生产代码：一次修复新增生产代码 1906 行、测试 3339 行，另一次 1038 行对 1811 行，58 行的小修复配了 108 行测试。一个"读到完成事件就关闭上游"的边界单独写了 251 行、4 个测试，其中一个还跑 2×2 矩阵。生产代码里，只有一种实现的内部依赖也要依次断言两种接口，都不满足再返回错误。
- **原因**：规则只说"先做最小实现"，没有说校验该放在哪一层、测试写到多少为止。agent 把每个分支和每种内部状态组合都当成需要防住、需要测试的风险。
- **对策**：规则写明只在系统边界校验，内部调用信任类型和调用方约定；测试只覆盖需求行为和真实出现过的 bug，测试量与改动相当。审交付时对比测试和生产代码的新增行数，测试明显更多时抽读几个用例。

## 15. 注释里堆满否定句

- **现象**：同一个网关项目由 agent 新写的那部分包里，2215 行注释有 465 行带 not、never、does not，典型句式是"X is an allowlist, not discovery""Y never consumes this view"。README 开头也连写了好几句"没有修改……不是……不会……"。
- **原因**：推测与第 7 条相同：规划和 spec 里的免责句被带进了注释和文档。
- **对策**：写作规则要求注释说明代码做什么、为什么，不罗列它不做什么；只有读者最容易误解的地方才写否定句。

## 16. 自建一致性协议

- **现象**：同一个项目由网关和多个 worker 组成，agent 新写的那部分生产代码里 epoch 出现 474 次、fence 375 次、generation 326 次，节点切换要经过多层 fence 和 epoch 校验，每一步之后都重新检查状态。修复这些协议本身的竞态，又占用了后续好几次修复提交。
- **原因**：遇到多节点一致性问题时，agent 倾向在应用层设计协议，而不是先看数据库已经提供的事务、行锁和唯一约束能否解决。
- **对策**：规则要求先用数据库机制；确有必要自建协议时，在设计里说明数据库机制为什么不够。审规划时看到 epoch、fence、lease 这类新词，要问清理由。

## 17. 修复提交夹带无关工作

- **现象**：一次标题为修复 worker 切换竞态的提交，同时改写了 4 份文档（1129 行），给 Go 仓库引入了 Node 测试工具链（package.json、jsdom 和 847 行的锁文件），删除了一个 719 行的文件，还新增了一个迁移命令。
- **对策**：规则里已有"一次改动只解决一件事"，但没有挡住。审交付时逐个看提交的 `--stat`，修复提交里出现文档重写、新工具链或新命令时，要求拆开。

## 18. 做不出好看的界面

- **现象**：同一个项目的前端 7,385 行 CSS，用了 41 种字号、约 20 种圆角。每个标题上方都有一行小字眉标，标题下还有一句复述标题的副标题，同一个数字在一屏里出现三四次。1440 宽的屏幕上，只有一行数据的表格就出现横向滚动。
- **原因**：只给文字要求（"简洁""专业"），agent 会用自己的默认样式去填，结果是卡片套卡片、处处是装饰。
- **对策**：先由能做设计判断的人或 agent 写一份可以在浏览器里打开的参考稿，再写一份精确到数值的设计规范，最后分阶段实施，每个阶段都截图审阅。做法见 `ui-redesign.md`。改造后 CSS 降到 4,490 行，字号 6 种，圆角 4 种。

## 19. "已自查"不可靠

- **现象**：manifest 里写着"逐条对照了规范"，但用量筛选仍然要求输入 ID，刷新按钮的样式、图表标题、行菜单文案都没有照规范做，而这些在规范里写得很明确。连续两个关卡都是这样。
- **原因**：自查清单只问"有没有违反禁止项"，没有要求逐条证明"做到了哪条要求"。
- **对策**：要求提交 `spec-check.md`，把规范原文逐条抄下来，每条填"是 / 否 / 部分"和证据截图，不符合的只能修正或列出，不能换成别的做法。引入之后，下一个关卡 141 条里 108 条"是"，"部分"大多是"还没截图"，真正的缺陷都被主动列了出来。模板见 `prompts/spec-check.md`。

## 20. 为了满足字面规则写出别扭的实现

- **现象**：规范写了"加载完成时布局不跳动"，它就给每个表格容器写死了 `min-height: 246px`，结果只有两行数据时，表格下方空出一大块。
- **原因**：规则只写了要求，没写这条要求要解决什么问题，agent 用最直接的方式满足字面。
- **对策**：规则同时写出本意和不允许的做法（"不要为了防止跳动给容器设固定高度"）。发现别扭的实现时，先检查是不是规则本身写得过严。

## 21. 做不到的功能做成占位

- **现象**：接口没有平均延迟、成员数、修改密码，页面就显示"平均延迟 —"、"成员 —"和一个禁用的"修改"按钮。
- **对策**：规则写明"做不到的就不显示"。顺带发现接口其实有延迟中位数，改用它。

## 值得保留的做法

- 如实报告：没做的、失败的门禁、跳过的测试都会单独列出。
- 被指出错误后会明确纠正，不会硬撑。
- 给了预算和单变量要求之后，实验设计很扎实：22 次真实请求就完成了定位和验证。
- 严格遵守写入边界，几乎不越界改文件。
