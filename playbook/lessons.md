# Codex 行为观察与对策

来源：一个由 Codex 在一周内写成的 Go/React 项目（约 6.6 万行生产代码、6.4 万行测试、5 万多词的文档和 spec），以及随后的审查、规范整理、门禁建设和一次线上问题排查。每一条按现象、原因、对策记录。

## 1. 照抄输入文本的文风和术语

- **现象**：代码注释里 exact、proof、fence、lineage 反复出现；界面文案里出现 "checked stop""fence new work" 这类工程术语。
- **原因**：spec 用压缩的法律条文体写成，数字和单词粘连，自造术语密集。agent 照着写。
- **对策**：先修 spec：制定写作规则，建立术语表，把文档改写为只描述当前状态。只加规则、不修输入，效果有限。

## 2. 空模板 spec 等于没有约束

- **现象**：目录结构和质量规范的 spec 还是 "(To be filled by the team)"。结果是 31 个后端包，最长的函数 437 行。
- **对策**：项目初期就从真实代码中归纳结构和质量规范，写明量化上限，并附上真实文件作为示例。

## 3. spec 被当成变更日志

- **现象**：每做一个功能就新增一份 spec，新规则用 "supersedes" 叠在旧规则上，阅读顺序要层层跳转。
- **原因**：spec 更新类技能要求"每次都沉淀契约"，但没有要求合并和改写。
- **对策**：写作规则要求只写当前状态、直接改写原文、优先合并进已有文档。

## 4. 材料不完整时下确定结论

- **现象**：根据一份被截断的 256 KiB 请求体，断言某类条目是"确定的不兼容项"。拿到完整采集后，发现真正的原因是另一类条目。
- **对策**：要求区分"假设"和"结论"。条件允许时，用真实复现和单变量对照来取证。

## 5. 字面执行停止条件，变得过度谨慎

- **现象**：提示词里写了"逐字节一致"和"复现不了就停下"。结果它因为 8 字节的时区差异，判定"未复现"并停下。
- **对策**：写清判定标准的本意，例如"错误码和参数一致即为复现"。把停止条件收窄到真正需要人决定的情况，见 `prompts/unblock.md`。

## 6. 倾向自建框架

- **现象**：为了豁免历史 lint 违规，计划新写两套脚本、JSON 基线和对应的测试，而 golangci-lint 和 ESLint 的原生机制就能做到。
- **对策**：要求优先使用工具的原生机制。审规划时专门看"新增了哪些脚本和框架"。

## 7. 规划冗长，免责句堆叠

- **现象**：300 多行的 design，反复出现 "does not authorize""is not proof of"。
- **对策**：提示词里给出篇幅上限，并明确"只写决策和步骤，不写免责声明"。下一次规划就降到了 115 行。

## 8. 意外的副作用

- **现象**：一次隐式的 `pnpm install` 用新版 pnpm 重写了锁文件，丢掉了安全版本覆盖。agent 发现了变更，却不知道来源。
- **对策**：要求安装依赖时冻结锁文件。提交前看 `git status`，用文件修改时间追查来源。Stop hook 会检查"锁文件变了，清单却没变"的情况。

## 9. 全局规则放大了热修复的 diff

- **现象**：在一个旧仓库做热修复时，为了满足"函数不超过 80 行、行不超过 120 字符"，顺手重排和拆分了周围的旧代码。一个小修复变成了 224 行的 diff。
- **对策**：长度规则只约束新写和修改的代码。Stop hook 对已经超长的旧函数，只在明显增长时提醒。不打算整改的旧仓库，可以用 `.codex-style.json` 关闭检查。

## 10. 停顿点是人介入最有价值的时刻

- **现象**：几次关键纠偏都发生在审规划时：度量脚本不该嵌进 spec、合并后的文件名沿用了旧术语、不该自建 lint 框架、不该绕过上游限制。
- **对策**：goal 模式只用于"决定已经写进任务文件"之后的执行阶段。

## 11. 会执行顺带写的授权

- **现象**：审阅回复末尾写了一句"改完直接 start 并实施"，它立即执行完了。而人还以为它在等审阅。
- **对策**：每条回复只给一个明确的动作指令，见 `review-checklist.md`。

## 12. 为了让功能可用，会提出绕过外部限制的方案

- **现象**：上游明确把某些工具保留给自己使用，并强制校验其 schema。为了绕过校验，它提出给这些工具改名伪装。
- **对策**：审规划时专门检查是否在规避服务方的明确限制。这类方案直接否决，改走服务方支持的路径，例如路由到合适的账户类型，或者返回可操作的错误。

## 13. 过时的指引会把 agent 引到错误的位置

- **现象**：项目 AGENTS.md 仍然指向另一个仓库的任务目录。
- **对策**：AGENTS.md 只写稳定的边界和门禁；任务的位置变化时，同步修改它。

## 值得保留的做法

- 如实报告：没做的、失败的门禁、跳过的测试都会单独列出。
- 被指出错误后会明确纠正，不会硬撑。
- 给了预算和单变量要求之后，实验设计很扎实：22 次真实请求就完成了定位和验证。
- 严格遵守写入边界，几乎不越界改文件。
