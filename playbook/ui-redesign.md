# 指挥 Codex 做界面改造

Codex 能按规格把界面实现得很准确，但自己做不出好看的设计。所以分工是：设计由人（或能做设计判断的 agent）定下来，写成可以照着做的东西；Codex 负责实现；每个阶段用截图审阅。

## 1. 先看真实界面

在本地隔离环境里把应用跑起来，逐页截图，桌面和手机、浅色和深色都要截，再配合代码统计找问题：

- 字号、圆角、颜色有多少种不同的取值；
- 眉标、统计卡、卡片容器出现了多少次；
- 同一个事实在一屏里出现了几次；
- 表格在 1280 和 1440 宽度下是否横向滚动；
- 加载时页面是否空白。

数字比形容词更能让 Codex 理解问题。

## 2. 写参考稿

用一个独立的 HTML 文件画出关键画面：外壳、一个列表页、一个概览页、空状态、抽屉表单、登录页。要求：

- 设计变量直接写在 `:root` 和 `[data-theme="dark"]` 里，取值就是要实现的值；
- 底部放一个切换画面和主题的工具栏，地址后加参数可以隐藏它，方便截图对比；
- 使用假数据，名字和邮箱统一用 `example.com`；
- 写完先自己截图检查：桌面、手机、深色模式都要看，手机端尤其容易出问题。

参考稿比任何文字描述都有效。Codex 照着具体的样子做，偏差最小。

## 3. 写设计规范

`design.md` 的结构：

1. **原则**：五到七条，例如"一个事实只说一次""一个页面一个主操作""做不到的就不显示"。
2. **设计变量**：颜色表（浅色 / 深色 / 用途），并写明对比度要求。
3. **排版**：允许使用的字号列表及用途。
4. **间距、圆角、尺寸**：只列允许的取值。
5. **控件**：按钮只有几种，各自的用途。
6. **外壳**：侧栏、用户菜单、手机端。
7. **页面模板**：页头、区块、次要操作放在哪里。
8. **通用模式**：表格、状态、空和加载和出错、抽屉和弹窗、表单、图表、代码块、设置行。
9. **逐页规格**：每页要保留什么、删除什么、表格有哪些列、菜单项的文案。
10. **文案规则**：不要用的词和句式。
11. **禁止清单**：一出现就说明做偏了的东西。
12. **截图自查清单**。

每条规则都要写出本意，必要时写出不允许的做法，否则 Codex 会用最直接的方式满足字面要求（见 `lessons.md` 第 20 条）。

## 4. 分阶段实施，每个阶段一个审阅关卡

| 阶段 | 内容 | 为什么这样分 |
| --- | --- | --- |
| 0 | 基线截图和度量 | 用来做前后对比 |
| 1 | 设计变量、基础控件、外壳、**一个试点页** | 试点页定下的模式会被复制到所有页面，审得最严 |
| 2 | 其余列表页 | 验证模式能推广 |
| 3 | 概览、统计、设置类页面 | 图表、统计条、设置行这些新模式 |
| 4 | 登录等认证页 | 用真实后端走一遍登录流程 |
| 5 | 清理死代码、更新 UI 规范、最终截图 | 每个阶段都删自己替换下来的旧样式，不要全部留到这里 |

- 截图规格要写死：尺寸、主题、状态（有数据、空、加载、出错）、文件命名规则、存放目录（被 git 忽略的目录）。
- 每个关卡都要提交 `spec-check.md`（模板见 `prompts/spec-check.md`），并报告 CSS 行数和未引用的类。
- 审阅时发现的是规范没写到的问题，就直接修订 `design.md` 和参考稿，再让 Codex 提交修订并重读，保证设计依据始终只有一份。
- 修正意见写得足够具体时，可以让它修完直接进入下一阶段，在下一个关卡一并检查，少走一轮来回。

## 5. 审阅截图时看什么

- 和参考稿中最接近的画面并排比较：间距、字号、颜色、对齐。
- 先读 `spec-check.md` 里的"否"和"部分"，再抽几张截图核对它的结论是否属实。
- 对照第 9 节的逐页规格，看文案、列、菜单项是否照做了。这里最容易漏。
- 用代码统计复核度量：字号和圆角的取值、`min-height` 写死的高度、颜色值是否都来自变量。
- 金额、时间、长名称这些用合成数据容易看不出问题，上线前要在真实数据上再看一遍。
